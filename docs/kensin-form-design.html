長崎北徳洲会病院 健康管理センター
この資料について

院内で作成済みの docs/01_要件定義.md〜06_サイトへの導線設置.md と CLAUDE.md をもとに、関係者へ共有できる 1 枚にまとめたものです。原本はリポジトリにあり、矛盾があった場合は原本が正です。読んでいて見つかった資料間の食い違いは 03 節に挙げました。

01目的

健診・人間ドックの予約受付が電話のみで、受付スタッフの電話対応負荷が高い。これを減らすことが目的であり、Web 化そのものが目的ではない。

判断に迷ったときの基準は 1 つだけです —— 受付スタッフの電話が 1 本減るか、1 本あたりが短くなるか。ここに効かない機能は作りません。

現状の課題

  • 受付は電話のみ。受診希望者は勤務時間中に電話する必要がある
  • 1 件あたりコース・胃部検査・補助券の有無・妊娠の可能性などを口頭で聞き取るため長い（仮・5〜10 分）
  • 聞き取り内容が受付担当 8 名それぞれの手元にあり、依頼の一覧が存在しない。対応漏れ・二重対応が起こりうる

期待効果

指標現状目標
受付可能時間9:00〜16:30（月〜土）＝ 7.5 時間/日24 時間
1 件あたりの電話時間（仮）5〜10 分3 分以下（確認と日程調整のみ）
依頼の一覧化なし全件が台帳に記録される
対応漏れ把握できていない未対応が台帳上で可視化される

03資料間の食い違い

既存資料を通して読んだ際に見つかった不整合です。どちらも「古い資料を単独で読むと、間違ったものを作ってしまう」類のものなので、原本への追記をおすすめします。

01要件定義書 §7 と F-06 が、採用しなかった案 B のまま残っている

01_要件定義.md（9/4 版）の §7 システム構成は「サイト上の PHP フォーム → 受付メール → メール本文の機械可読ブロックを GAS が解析して起票」と書かれています。しかし CLAUDE.md（9/15）で案 D を採用しており、GAS からスプレッドシートへ直接書くためメール解析による起票は不要です。F-06「受付通知メールを解析し、スプレッドシートに1行追加」も同じく案 B 前提です。要件定義書だけを読んだ人は、作る必要のない解析処理を実装してしまいます。

推奨01_要件定義.md の §7 と F-06 の冒頭に「案 D 採用により無効。CLAUDE.md を参照」と 1 行追記する。削除ではなく無効の明示にしておくと、案 B へ切り戻すときにそのまま使える。

02電話受付時間が、要件定義書とサイト調査メモで食い違っている

01_要件定義.md §1.1 は「午前 9:00〜12:00／午後 17:00〜20:00（仮・要確認）」、期待効果の表は「平日・土 計 6 時間/日」。一方 04_サイト調査メモ.md は公式サイトの実地調査として 9:00〜16:30（月〜土）を確認し、「前回までの記載は誤りでした」と明記しています。04 が正ですが、01 側は直っていません。

推奨01 の §1.1 と期待効果の表を 9:00〜16:30（＝7.5 時間/日）に修正する。この資料の 01 節の表は修正後の値で書いてあります。自動返信メールや導線ページの文言にも同じ時間が出るため、ここがずれたまま公開すると申込者への案内が誤りになる。

04全体の流れ

業者
予約・お問い合わせページにリンクを 1 本足す電話案内より上に置く。下に置くと電話をかける人が減らず、目的を果たさない。文言は「予約する」ではなく「予約を依頼する」。
申込者
フォームに入力する（24 時間）区分とコースを選ぶと、関係する項目だけが出る。希望日は受付可能日カレンダーから最大 3 つ。
GAS
サーバ側で再検証し、受付番号を採番する選ばれた日がその時点でも受付可能かを再確認。採番は LockService で排他（重複すると台帳が壊れる）。
GAS
台帳へ 1 行追加し、メールを 2 通送る受付担当へ通知、申込者へ自動返信。ステータスの初期値は「未対応」。
受付担当
翌朝、台帳の「未対応」を確認して電話する安全確認に「該当あり／わからない」がある行は色が付く。必要なら健診担当医に相談。
受付担当
日程を確定し、ステータスを更新する担当者名と確定日時を入力。既存の予約台帳へ転記（当面は二重入力を許容）。
受付担当
受付可能日シートを毎朝更新するこの運用が止まるとフォーム全体が使えなくなる。枯渇・未更新は GAS が自動通知する（07 節）。

05入力項目と分岐

分岐の目的は見た目ではなく、受付担当が折り返し電話で聞き直す項目をゼロに近づけることです。非表示の項目は送信データから除外し、台帳では空欄になります。

グループ項目表示条件必須
A 共通氏名／フリガナ／生年月日／性別／電話番号／メール／連絡希望時間帯／受診歴常時すべて必須
A 共通第 1〜第 3 希望（日付＋午前・午後）常時。受付可能日からのみ選択第 1 希望のみ必須
B 区分支払方法（現金／カード）個人（全額自己負担）必須
B 区分保険証の記号・番号／被扶養者の同時受診協会けんぽ必須
B 区分健保組合名／補助券の有無健康保険組合の補助必須
B 区分市町名／受診券の有無自治体の特定健診・がん検診必須
C コース胃部検査（胃カメラ／バリウム／希望しない）胃部検査を含むコース必須
C コース鎮静剤の希望胃部検査＝胃カメラ必須
D 追加検査8 項目から複数選択常時任意
E 安全確認妊娠中・妊娠の可能性・授乳中性別＝女性必須

安全確認欄の設計（厳守）

回答は「該当あり／該当なし／わからない」の 3 択のみ。病名・薬剤名・症状は取得しません。詳細は折り返しの電話で聞き取ります。平文メールとクラウド台帳に残る要配慮個人情報を最小化するための設計であり、親切心で自由記述欄を足さないでください。

06スコープ外

作らないもの理由将来
空き枠のリアルタイム表示枠管理が紙・Excel 運用。Web 連携すると二重管理になる検討
Web 上での予約確定安全確認と枠調整に人の判断が必要対応しない
事業所健診・雇入時健診の申込複数名一括で入力構造が全く異なる第 2 弾で別フォーム
オンライン決済当日窓口精算で運用できている対応しない
電子カルテ・健診システム連携IF 仕様・費用が未確認検討
変更・キャンセルの Web 受付本人確認の仕組みが必要当面は電話
ログイン・マイページ年 1 回の利用にアカウントは過剰対応しない
添付ファイルの受け取り個人情報の保管責任が増える対応しない

07受付可能日カレンダー

申込者に日付を自由入力させず、受付担当がスプレッドシートに入力した日だけを選べるようにします。これは空き枠管理ではありません —— ◯を入れた日＝「申し込みを受け付ける日」であって、「予約が確定できる日」ではありません。

[スプレッドシート「受付可能日」]  ← 健診受付8名が編集
        │  GASが10分ごとにJSONを生成・公開
        ▼
   受付可能日JSON（日付と時間帯のみ。個人情報は含まない）
        │
        ├──→ [フォーム] 選べる日だけを濃く表示。それ以外は押せない
        └──→ [サーバ側] 送信時に同じJSONで再検証（改ざん・時間差対策）
このシステム最大の弱点

このカレンダーは、更新が止まった瞬間にフォーム全体が使えなくなります。気づく仕組みがないと、申し込みがゼロになった理由が誰にも分かりません。選択可能日が 7 日分を下回ったとき、および 3 日以上更新がないときに GAS が受付担当と情シスへ通知します（F-13）。この通知は必須機能です。

取得に失敗したとき・候補が空のとき

カレンダーを隠し、電話案内に切り替えます。空のカレンダーを出さないこと。申込者が「押せる日がない画面」を見て諦めるのが最悪の結果です。04 タブで、候補を空にしたときの表示を実際に確認できます。

送信時の再検証（省略不可）

ページを開いたまま数時間放置して送信されると、すでに受付を止めた日の依頼が入ります。送信時にサーバ側でも受付可能日を取得し、選ばれた日付と時間帯を再確認してください。不一致なら「選択された日は受付が終了しました。お手数ですが選び直してください」と表示します。

09個人情報の扱い

  • 含まれる情報：氏名、フリガナ、生年月日、性別、電話番号、メール、保険証記号番号（区分による）、受診希望内容、安全確認 3 択の回答
  • 要配慮個人情報：妊娠・体内金属・アレルギー・服薬は健康状態に関する情報。該当の有無（3 択）のみを取得し、病名・薬剤名は取得しない
  • 保管場所：（仮）Google スプレッドシート。「リンクを知る全員」は使わず、8 名＋情シスの個人アカウントを個別に追加
  • アカウント：無償 Gmail の寄せ集めではなく Google Workspace を推奨。退職者のアカウントを病院が止められないため（docs/05_台帳の限定共有.md）
  • 保持期間：（仮）1 年。経過後は CSV へ退避してから台帳から削除

確定した健診の記録は既存の健診システム側が正本です。この台帳は予約依頼の受付記録であって、健診記録ではありません。

10主なリスク

リスク影響対応
受付可能日の更新が止まり、選べる日がなくなる大枯渇（7 日分未満）・未更新（3 日）を GAS が自動通知。枯渇時は電話案内へ切り替え
Google クラウド利用が規程上認められない大案 B へ全面切り替え。8 名の同時編集ができなくなるため、ステータス更新は当番制にする
通知メールが迷惑メール判定され届かない大SPF を事前確認。試験時に 3 系統へ着信確認。加えて、台帳に 24 時間以上「未対応」があれば気づける運用にする
依頼が来ても誰も見ていない（休日明け等）中自動返信で「2 営業日以内」と明示して期待値を下げる。日次確認の当番を決める
台帳から既存予約台帳への二重入力中当面は許容。台帳の列順を既存台帳に合わせ、転記を機械的にできる形にする
開いたまま放置して送信され、締切後の日が入る中送信時のサーバ側再検証（07 節）
受付可能日 JSON が匿名公開で外部から見える中個人情報は含まないが、公開の可否を院内で確認（未決 #10）
作成者（情シス 1 名）の不在時に台帳側が壊れる中GAS のコードと台帳構成を院内サーバに文書保管。復旧手順を 1 枚にまとめる

    03台帳試作

    スプレッドシート「予約依頼台帳」の見え方です。受付担当が更新する運用列 A〜F を左端に置くのが要点で、右へスクロールしないと仕事にならない並びにすると使われなくなります。

    条件付き書式

    C 列が「未対応」かつ B 列から 24 時間経過 → 行が赤。安全確認列が「該当あり」「わからない」 → セルが黄。どちらも、電話の前に気づくべきことを色で示しています。データはすべて架空です。

    予約依頼台帳 · 受付中シート共有：受付 8 名＋情シス（個別に追加）
    A受付番号 B受付日時 Cステータス D対応担当 E確定日時 F確定コース G氏名 K電話番号 M連絡希望 O/P第1希望 U希望コース V/W胃部検査 Y妊娠等 AB血液サラサラ AC車いす

    ステータスと対応担当は、この表の中で変更できます（試作のため保存されません）。「未対応」以外にすると赤が消えることを確認してください。

    列の設計で決めてあること

    • 運用列（A〜F）は受付担当が更新し、申込内容列（G 以降）は GAS が書く。手で編集しない列はシート保護をかける
    • 分岐で表示されなかった項目は空欄。空文字と「未表示」を区別するため、GAS 側ではキー自体を出力しない
    • 区分ごとの追加項目（保険証記号番号など）は列を増やさず AD 列に JSON 文字列で持つ
    • シートは「受付中」と「完了済（年度別）」に分け、確定・キャンセルから 3 か月経過した行を年次で移す
    • 列順は既存の予約台帳に合わせる。転記が機械的にできる形にしておくと、二重入力の負担が減る
