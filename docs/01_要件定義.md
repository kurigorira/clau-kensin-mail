## 1. 背景と目的

### 1.1 現状の課題

- 健診・人間ドックの予約受付は **電話のみ**。受付時間内（9:00〜16:30、月〜土。日・祝日・年末年始は休み）に限られる。（2026-09-04のサイト調査で確認。旧記載「午前9:00〜12:00／午後17:00〜20:00」は誤りだった）
- 受診希望者は勤務時間中に電話する必要があり、機会損失が生じている（件数は未計測）。
- 電話1件あたり、コース・胃部検査の選択・補助券の有無・妊娠の可能性などを口頭で聞き取るため、所要時間が長い（（仮・要確認）1件5〜10分）。
- 聞き取り内容は受付担当8名それぞれの手元で管理されており、**依頼の一覧が存在しない**。対応漏れ・二重対応が発生しうる。

### 1.2 このシステムで実現すること

Webフォームから24時間、健診・人間ドックの**予約依頼**を受け付ける。依頼内容は受付担当が共有する台帳（スプレッドシート）に自動で1行として起票され、8名の誰が対応中かが一目でわかる状態にする。予約の確定は従来どおり折り返しの電話で行う。

### 1.3 期待効果

| 指標 | 現状 | 目標 |
|---|---|---|
| 受付可能時間 | 月〜土 計7.5時間/日 | 24時間 |
| 1件あたりの電話時間 | （仮）5〜10分 | 3分以下（確認と日程調整のみ） |
| 依頼の一覧化 | なし | 全件が台帳に記録される |
| 対応漏れ | 把握できていない | 未対応が台帳上で可視化される |

## 2. 利用者と利用シーン

| 利用者区分 | 人数 | 主な操作 | 利用頻度 | 利用端末 |
|---|---|---|---|---|
| 受診希望者（個人） | 月20〜100件（仮・要確認） | フォーム入力・送信 | 1人あたり年1回 | スマートフォン中心 |
| 健診受付担当 | 8名 | 台帳の確認、折り返し電話、ステータス更新 | 毎日 | 院内PC |
| 情報システム担当 | 1名（作成者） | 台帳の保守、項目変更、バックアップ | 月1回程度 | 院内PC |
| 外部サイト制作業者 | － | フォーム画面の実装・設置 | 構築時のみ | － |

### 2.1 主要な利用シーン

**シーン1：受診希望者が申し込む（夜間）**
21時、スマートフォンで病院サイトを開く → トップページの「健診・人間ドック 予約依頼」ボタンを押す → コースを選ぶと、そのコースに関係する項目だけが表示される → 希望日を第3希望まで入力 → 確認画面で内容を見直して送信 → 「受付しました。予約確定ではありません。2営業日以内に病院からお電話します」という自動返信メールが届く。

**シーン2：受付担当が対応する（翌朝）**
9時、共有スプレッドシートを開く → ステータス「未対応」の行を確認 → 内容を見て、その場で空き枠を確認できる状態にしてから電話 → 日程を確定 → ステータスを「予約確定」に変更し、担当者名と確定日時を入力 → 既存の予約台帳へ転記。

**シーン3：判断に迷う依頼が来た場合**
安全確認欄に「該当あり」または「わからない」が入っている依頼（妊娠の可能性、体内金属、抗血栓薬など）は、台帳上で色が付く（条件付き書式）。受付担当は電話時に必ずその項目を確認し、必要なら健診担当医に相談する。

### 3.1 主要機能の詳細

#### F-01 予約依頼フォーム（入力）

- **目的**：受付担当が折り返し電話で聞き直す項目をゼロに近づける。
- **入力**：後述「§6.1 入力項目と分岐条件」のとおり。
- **処理**：受診区分とコース選択に応じ、関連項目のみをJavaScriptで表示・非表示する。非表示の項目は送信データから除外する。
- **出力**：確認画面へ遷移。
- **受け入れ条件**：
  - コースに「胃部検査」を含むものを選んだときのみ、「胃カメラ／バリウム／希望しない」の選択肢が表示されること。
  - 上記で「胃カメラ」を選んだときのみ、「鎮静剤の希望」と「血をサラサラにする薬の内服」が表示されること。
  - 性別で「女性」を選んだときのみ、「妊娠の可能性・妊娠中・授乳中」が表示され、かつ必須となること。
  - オプションで「頭部CT・MRI」を選んだときのみ、「ペースメーカー・体内金属」「造影剤アレルギー」が表示されること。
  - JavaScriptが無効な環境では、全項目が表示された状態で入力・送信できること。

#### F-02 入力チェック

- **目的**：受付担当が連絡できない依頼（電話番号の誤り等）を防ぐ。
- **処理**：クライアント側とサーバ側の**両方**で検証する。サーバ側の検証を必須とする。
- **受け入れ条件**：
  - 必須項目が未入力のとき、送信されず、該当項目に日本語のエラーが表示されること。
  - 電話番号が数字とハイフン以外を含むとき、エラーとなること。
  - 希望日が1件も選択されていないときエラーとなること。
  - 送信時、サーバ側でも受付可能日データを取得し、選択された日付・時間帯が受付可能であることを再検証すること。不一致の場合は送信を受け付けず、選び直しを促すこと。

#### F-04 受付通知メール（院内宛）

- **目的**：受付担当への即時通知と、台帳起票の元データを兼ねる。
- **出力**：件名 `【健診予約依頼】<受付番号> <氏名> / <コース名>`
- **本文**：前半に人が読む整形テキスト、後半に機械可読ブロックを置く。

```
========== 以下はシステム処理用（編集しないでください） ==========
#DATA_BEGIN
{"uketsuke_no":"20261201-0001","name":"...","kana":"...", ... }
#DATA_END
```

- **受け入れ条件**：
  - 送信元アドレスが病院ドメインであり、SPFを通過して受付用メールボックスに届くこと（迷惑メールフォルダに入らないこと）。
  - 機械可読ブロックがJSONとして解析可能であり、非表示だった項目はキー自体を含まないこと。
  - 日本語が文字化けしないこと（UTF-8、件名はMIMEエンコード）。

#### F-05 自動返信メール（申込者宛）

- **受け入れ条件**：
  - 本文に「これは受付の確認であり、予約の確定ではありません」という趣旨が、冒頭3行以内に含まれること。
  - 折り返し連絡の目安（（仮）2営業日以内、日祝を除く）が明記されていること。
  - 受付番号が記載されていること。
  - 入力された情報のうち、健康状態に関する項目は返信メールに**含めない**こと。

#### F-06 台帳への自動起票

> **この項は案D採用により無効です（CLAUDE.md「方式の決定」を参照）。**
> 案Dでは、GAS Webアプリが送信を受けてスプレッドシートへ直接1行追加するため、メール本文の解析による起票は行いません。以下は**案Bへ切り戻した場合の仕様**として残しています。

- **処理**：受付用メールボックスを1〜5分間隔で監視し、未処理メールの機械可読ブロックを解析してスプレッドシートに1行追加、処理済みラベルを付与する。
- **受け入れ条件**：
  - 受付番号が既存行と重複する場合、新規行を追加せず、エラーとして記録すること（二重起票の防止）。
  - 解析に失敗した場合、行を追加せず、当該メールに「要確認」ラベルを付け、情報システム担当へ通知すること。
  - 起票された行のステータス初期値が「未対応」であること。

## 4. スコープ外（今回作らないもの）

| 項目 | 理由 | 将来対応 |
|---|---|---|
| 空き枠のリアルタイム表示 | 枠管理が既存の紙・Excel運用であり、Web連携すると二重管理になる | 検討 |
| Web上での予約確定 | 安全確認と枠調整に人の判断が必要 | 対応しない |
| 事業所健診・雇入時健診の申込 | 複数名一括申込のため入力構造が全く異なる。**別導線とする** | 第2弾で別フォームを作成 |
| オンライン決済 | 当日窓口精算で運用できている | 対応しない |
| 電子カルテ・健診システムとの連携 | 部門システムのIF仕様・費用が未確認 | 検討 |
| 予約の変更・キャンセルのWeb受付 | 本人確認の仕組みが必要 | 検討（当面は電話） |
| ログイン機能・マイページ | 年1回の利用にアカウントは過剰 | 対応しない |
| 添付ファイル（受診券の画像等） | 個人情報の保管責任が増える | 対応しない |

**F. 備考（任意・全角150字以内）**

### 6.2 個人情報・機微情報の扱い

- **含まれる情報**：氏名、フリガナ、生年月日、性別、電話番号、メールアドレス、保険証記号番号（区分により）、健診の受診希望内容、安全確認3択の回答
- **要配慮個人情報の扱い**：妊娠・体内金属・アレルギー・服薬は健康状態に関する情報にあたる。フォームでは**該当の有無（3択）のみ**を取得し、病名・薬剤名は取得しない。これにより、平文メールとクラウド台帳に保持される機微情報を最小化する。
- **保管場所**：Googleスプレッドシート（**Google Workspace** アカウントによる限定共有。2026-09-16 承認条件）。受付メールは受付用メールボックス。
- **アクセスできる者**：健診受付担当8名、情報システム担当1名。閲覧・編集権限は個人アカウント単位で付与し、リンクを知る全員への共有は行わない。
- **関連する院内規程**：個人情報保護規程、および外部クラウドサービス利用に関する徳洲会本部の基準（**要確認・未決事項#1**）。

## 7. システム構成（案）

> **本節は案B（サイト内PHPフォーム）を前提とした構成であり、現在は無効です。**
> 採用したのは案D（GAS Webアプリ＋スプレッドシート直書き）です。最新の構成は CLAUDE.md「方式の決定」を参照してください。本節は、Googleクラウド利用が院内規程で認められず案Bへ切り戻す場合の仕様として残しています。

- **稼働環境**：既存の公式サイトと同一のWebサーバ（（仮）PHPが動作する共用レンタルサーバ）
- **技術構成**：

```
[受診希望者] スマホ・PC
      │ HTTPS
      ▼
[公式サイト] reservation_form.php（入力）
             → reservation_confirm.php（確認）
             → reservation_send.php（送信・検証・メール発行）
      │
      ├─→ 受付用メールボックス（院内宛・機械可読ブロック付き）
      │         │ 1〜5分間隔で監視
      │         ▼
      │   [GAS] 解析 → スプレッドシート「健診予約依頼台帳」へ1行追加
      │                        │
      │                        ▼
      │                受付担当8名が閲覧・ステータス更新
      │
      └─→ 申込者宛 自動返信メール
```

- **既存システムとの関係**：連携しない。台帳から既存の健診予約台帳への**転記が1回発生する**（§9 リスク参照）。
- **選定理由**：
  - フォーム画面は既存サイトと同じPHPで作れば、外部業者が既存の保守範囲内で実装でき、追加費用と調整コストが最小になる。
  - 台帳側（GAS＋スプレッドシート）を業者に含めないことで、**項目追加やコース名改定を自分で直せる**。保守できる人が1名しかいないため、責任分界点をここに置くことを最優先とした。
  - メール本文に機械可読ブロックを埋め込む方式にすることで、業者側の実装は「決められた形式の文字列を出力する」だけで済み、台帳側の変更が業者作業を伴わない。

## B. データモデル（スプレッドシート「健診予約依頼台帳」）

**運用列（A〜F：受付担当が更新する。左端に置くことが重要）**

```
A 受付番号        TEXT  YYYYMMDD-NNNN（重複不可）
B 受付日時        DATETIME
C ステータス      TEXT  未対応 / 連絡中 / 予約確定 / キャンセル / 不成立
D 対応担当        TEXT  プルダウン（受付8名）
E 確定日時        DATETIME
F 確定コース      TEXT
```

**申込内容列（G以降：GASが書き込む。手で編集しない）**

```
G  氏名            L  メールアドレス      Q  第2希望日     V  胃部検査
H  フリガナ        M  連絡希望時間帯      R  第2希望時間帯 W  鎮静剤希望
I  生年月日        N  受診歴              S  第3希望日     X  オプション（カンマ区切り）
J  性別            O  第1希望日           T  受診区分      Y〜AC 安全確認5項目
K  電話番号        P  第1希望時間帯       U  希望コース    AD 区分別の追加項目（JSON文字列）
AE 備考            AF 送信元IP            AG 起票日時
```

- 分岐で表示されなかった項目は**空欄**とする。
- AD列は区分ごとに項目が異なるため、列を増やさずJSON文字列で保持する。
- 条件付き書式：C列が「未対応」かつ B列から24時間経過 → 行を赤。安全確認列に「該当あり」「わからない」 → セルを黄。
- シートは「受付中」と「完了済（年度別）」に分け、確定・キャンセルから3か月経過した行を年次で移す。

```
■ MVP（まずここまで）
1. 選択肢定義（コース・オプション・区分）を1ファイルにまとめる
2. フォーム画面（分岐なしの全項目表示版）＋サーバ側検証

■ 第2段階
6. JavaScriptによる項目の出し分け（分岐）
7. 条件付き書式・未対応アラート
```

**MVPで分岐を後回しにする理由**：分岐は見た目の改善であり、全項目が表示されていても業務は回る。先に「メールが届く・台帳に載る」を確定させるべきで、ここが動かなければ分岐を作っても意味がない。

## E. 試用時の確認ポイント

- 受付担当8名が、説明なしにステータスを更新できるか
- 折り返し電話が、実際に3分以内で終わるか。終わらない場合、何を聞き直しているか（→その項目をフォームに追加する）
- 受付メールが全員に確実に届いているか。迷惑メールフォルダを1週間毎日確認する
- 「決めていない・相談したい」を選ぶ人の割合。多い場合は選択肢の説明が不足している
- 想定していない使われ方（家族分をまとめて申し込もうとする等）が出ていないか
